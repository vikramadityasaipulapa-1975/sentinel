# SENTINEL — Codex Master Implementation Plan
**Version:** 1.0 | **Approach:** learning-first, incremental, test-driven | **Status:** planning document

> Sentinel is an AI-assisted incident response and reliability platform. It observes an instrumented demo application, detects incidents, gathers telemetry and deployment evidence, proposes ranked hypotheses, retrieves runbooks, and supports explicitly approved sandbox remediation with recovery verification.

**Operating rule:** This file is the roadmap, NOT permission to implement all phases. Codex must complete exactly one approved task at a time. Do not silently advance.

## 2. Product scope and engineering principles
### Target demonstration
A faulty payment-service deployment at 14:07 produces increased checkout failures at 14:11. Prometheus shows the error-rate increase, Loki shows database timeout logs, and deployment records show a candidate change. Sentinel creates an incident, investigates using read-only tools, retrieves a related runbook, ranks hypotheses with citations, proposes rollback, waits for authorized human approval, executes a tightly scoped sandbox rollback, and checks fresh metrics for recovery.

**Never hardcode the answer.** The demonstration must use telemetry generated by the demo services. A timestamp relationship alone is not proof of causation. Show uncertainty and alternative explanations.

### Non-goals for MVP
No unrestricted autonomous shell, no production remediation, no multi-tenant billing, no Kafka, no automatic Kubernetes changes, no six-agent swarm, no fine-tuning, no complex microservice mesh.

### Architecture boundaries
- **Demo application:** checkout calls payment; both emit logs/metrics/traces and carry deployment metadata.
- **Observability:** Prometheus for metrics, Loki for logs, Tempo for traces; exporters/collectors are independent of AI.
- **Sentinel API:** owns users, incidents, approvals, deployment registry, audit history and external REST/SSE interface.
- **Worker:** consumes queued investigation jobs; invokes AI engine; persists status/events. Decide ownership explicitly to avoid double-processing.
- **AI engine:** read-only investigation tools, evidence normalization, hypothesis synthesis and RAG; cannot directly execute privileged remediation.
- **Action executor:** narrowly scoped sandbox operations, authorization and idempotency enforced server-side.

## 3. Common conventions and contracts
- All timestamps are UTC ISO-8601 with offsets; preserve event time and ingestion time separately.
- IDs are UUIDs; requests carry `request_id`; distributed calls propagate `trace_id` when available.
- API errors follow a consistent `{error:{code,message,details?},request_id}` shape; never leak secrets.
- Validate every request at the boundary; apply rate limits, payload limits and timeouts.
- API version prefix: `/api/v1`; document contracts in OpenAPI where feasible.
- Statuses: incident `OPEN | INVESTIGATING | MITIGATING | RESOLVED | CLOSED`; investigation `QUEUED | RUNNING | COMPLETED | PARTIAL | FAILED`; action `PROPOSED | PENDING_APPROVAL | APPROVED | REJECTED | EXECUTING | SUCCEEDED | FAILED | EXPIRED`.
- Agent outputs must contain evidence references and explicitly label observations, hypotheses and recommendations.
- Database migrations have one owner; no auto-sync against shared tables in production-like environments.
- Make queue jobs idempotent and retryable; avoid at-most-once assumptions for side effects.
- Record dependency versions in lockfiles; pin Docker images to stable versions, not `latest`, after the first prototype.

## 6. Fault-injection test matrix
| Scenario | Ground truth | Expected evidence | Failure to avoid |
|---|---|---|---|
| Payment deployment regression | New payment version introduces timeout | release time, timeout logs, increased p95/5xx | treating timing alone as proof |
| DB saturation without release | Connection pool exhausted by load | active connections, timeouts, no deployment | blaming most recent old deployment |
| Payment dependency 503 | Simulated downstream outage | payment 503 logs, checkout errors, traces | claiming checkout code bug |
| Traffic spike | Load overwhelms capacity | request rate rises before latency | misidentifying deployment |
| Missing Loki | Log backend unavailable | metrics and deploys still available | fabricating log evidence |
| Stale telemetry | Metrics delayed | freshness timestamps | pretending values are live |
| Malicious log instruction | Prompt injection in log body | log treated as data only | executing log-provided instructions |
| Concurrent approvals | Two users click approve | one action execution ID | duplicate rollback |
| Failed rollback | Bad version remains | post-action health check fails | marking incident resolved automatically |

## 7. Security and reliability requirements
- Authentication and RBAC at API, not merely hidden frontend controls.
- Read-only AI investigation credentials; separate action-executor identity and minimal permissions.
- Do not expose arbitrary PromQL/LogQL to unauthenticated users; validate ranges, service IDs and query cost.
- Webhook authentication and deduplication; restrict network ingress and use secrets outside source control.
- Validate structured LLM output against a schema; do not trust model confidence as calibrated probability.
- Treat retrieved runbooks, logs and incident descriptions as untrusted input; resist prompt injection.
- Human approval must specify exact action, target, version, expiry and approver. Recheck current state before execution.
- Enforce idempotency, audit trails, bounded retries, backoff, timeouts and rate limits.
- Sandbox-only write actions in the portfolio project; no real customer environments.
- Protect PII in logs; set data retention limits and avoid storing raw secrets in evidence.
